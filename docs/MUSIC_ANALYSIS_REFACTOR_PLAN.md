# 音乐结构与动态分析改造说明

本文供后续维护者直接据此拆任务和修改代码。目标是在不破坏现有推荐功能的前提下，让系统能更可信地描述一首歌的段落重复关系、动态起伏和编曲变化。当前推荐引擎位于 `music-recommend`；桌面播放器 `w-music` 通过本地服务调用它。

## 1. 改造目标

给一首完整音频，系统应尽量回答：

1. 音乐在什么时间发生了明显变化？
2. 哪些片段彼此重复或相似？
3. 全曲的动态如何变化，何处堆叠、抽空、达到峰值、回落？
4. 哪些片段可能是主歌、副歌、桥段等？判断依据和可信程度如何？
5. 哪些配器、人声或和声变化可以从混音中得到支持？

必须把“检测到音乐边界”“片段彼此相似”“片段的歌曲功能标签”作为三种不同结果。检测到边界，不代表系统已经知道它是副歌；两个片段相似，也不代表一定是同一段副歌。证据不足时应返回未知或候选判断，不要生成确定标签。

## 2. 当前实现和主要问题

相关实现集中在：

- `src/music_recommender/features/extract.py`：读取音频、协调各特征模块，并选择分析窗口。
- `src/music_recommender/features/structure.py`：粗略分段、能量曲线、段落类型启发式标签。
- `src/music_recommender/features/instruments.py`：频段能量比例及 HPSS 打击成分比例。
- `src/music_recommender/features/vocal.py`：低置信度的人声存在与音高估计。
- `src/music_recommender/features/harmony.py`：基于 chroma 模板的和弦估计。
- `src/music_recommender/recommendation/space.py`：用现有特征计算歌曲间相似度。
- `src/music_recommender/database/schema.py`、`database/repository.py`：分析结果的持久化。
- `configs/config.yaml`：当前配置默认 `audio.max_analysis_seconds: 45`。

### 2.1 结构标签目前不可靠

`structure_features()` 对输入片段计算 RMS、谱对比等信息，再调用 librosa 的 agglomerative segmentation。随后 `_label_segments()` 无论实际曲式如何，都会把第一段标为 intro、最后一段标为 outro；响度高于全曲片段最大值 70% 的片段倾向标 chorus；较安静片段标 verse；剩余片段按位置交替标 chorus/verse。这里没有依据旋律、重复性或歌曲位置验证标签，也没有预副歌识别。

这意味着当前 `segment_type_sequence` 是启发式占位结果，不能作为精确曲式标注。特别是安静副歌、响亮主歌、无前奏/尾奏歌曲、全曲一段或两段的歌曲，容易得到误导性标签。

### 2.2 动态曲线只覆盖分析窗口

`extract()` 先调用 `_analysis_window()`。配置默认取全曲最响的连续 45 秒，然后把这个窗口送入结构分析。因此 `energy_curve` 不是全曲曲线，可能漏掉前奏、预副歌、桥段和尾奏。用它描述整首歌的渐强或高潮位置会产生系统性偏差。

### 2.3 “乐器层数”和“和声层”目前并未识别

`instruments.py` 的低/中/高频比例只是频率能量分布；HPSS 把声音粗略拆成谐波成分和打击成分，不会告诉我们有几轨乐器，也不等价于鼓、钢琴、吉他分类。`vocal.py` 也没有检测合唱层数或和声进入位置。因此当前字段只能描述代理信号，不能输出“出现两层弦乐/三层和声”这类事实陈述。

### 2.4 和弦模板有确定的实现错误

`harmony.py` 中 `MAJOR` 和 `MINOR` 的数组注释说是三和弦，但数组实际表示音阶轮廓；模板创建时也没有按根音平移。只读检查当前 24 个候选模板，发现只有 2 个不同向量，C 与 D 的模板完全相同。这会让根音比较失去意义。应先修复，再用音频样本核对和弦输出。

## 3. 建议的数据结果

建议为分析结果增加明确版本号，例如 `analysis_version`，并把下列内容保存到结构 JSON；原有推荐用的标量列可以继续保留，避免一次性破坏数据库和客户端。

```json
{
  "analysis_version": 2,
  "analysis_scope": "full_track",
  "duration_seconds": 213.4,
  "segments": [
    {
      "start": 0.0,
      "end": 14.2,
      "group": "A",
      "label": "intro",
      "label_confidence": 0.71,
      "boundary_confidence": 0.88,
      "evidence": ["texture_change", "no_lead_vocal"]
    }
  ],
  "dynamics": {
    "time_seconds": [],
    "rms_db": [],
    "onset_density": [],
    "low_band_energy": [],
    "spectral_brightness": [],
    "arrangement_change": []
  },
  "events": [
    {"time": 86.0, "type": "build", "confidence": 0.76}
  ]
}
```

字段约定：

- `group` 表示重复关系，例如 A/B/C；它不承诺段落的语义名称。
- `label` 可取 intro、verse、pre_chorus、chorus、bridge、instrumental、outro、unknown。没有可靠模型判断时用 `unknown`。
- `boundary_confidence`、`label_confidence` 分开存；段落边界可靠，不代表功能标签也可靠。
- `evidence` 记录产生判断的可解释线索。建议枚举值稳定、可供 UI 展示。
- `dynamics` 的时间轴覆盖完整曲长。曲线采样间隔需固定并存入元数据，不要只存无法还原时间位置的 64 个均分值。
- 模型的置信度分数在验证前只能称为模型分数；应通过人工标注集校准后，才作为概率解释。

## 4. 推荐的分析流程

### 阶段 A：修正现有特征的含义和基础错误

1. 修复 `harmony.py` 的和弦模板。每个模板需由根音和三度/五度音构成，并按 12 个根音正确平移；大三和弦与小三和弦模板分别检查。避免把“音阶轮廓”误当成“三和弦模板”。
2. 在若干已知调性的短音频上检查 chroma 匹配，记录预测和弦、置信差值以及无法判断的情况。修复之前，不应继续把旧模板产出的根音序列当成可靠和弦证据。
3. 统一现有字段命名：`drum_energy_ratio` 应明确是打击性成分代理量，不应在 UI 或提示语里简称为真实鼓组占比；`vocal_ratio` 应注明低置信度估计。

### 阶段 B：整曲动态分析，保留推荐的快速路径

1. 将“推荐特征窗口”和“全曲结构分析”分开。推荐引擎若受性能限制，可继续用当前 45 秒窗口计算较贵的音高/和弦特征；结构分析则遍历完整音频，至少计算分帧 RMS、频带能量、谱变化和 onset 活动。
2. 动态计算使用有时间戳的短帧序列，再按固定时间间隔聚合。保留实际秒数、采样间隔、是否全曲分析等元信息。
3. 输出多条曲线，至少包括 RMS dB、打击性/onset 活动、低频能量、谱亮度。不要把所有变化压成一个“情绪强度”数字。
4. 事件标签（build、drop/pull-back、peak、release）从平滑后的曲线变化和相邻窗口对比产生，并保留证据与置信度。峰值可由多特征共同判断，不能仅凭单帧响度最大值。
5. 归一化时同时保留原始可比尺度和曲内相对尺度。仅用每首歌自己的最大值归一化，无法表达不同歌曲的实际响度差异。

### 阶段 C：先分段，再识别重复段落

1. 用节拍或小节对齐帧级特征，避免边界任意落在小节中间。输入不足以可靠追踪节拍时允许退回时间帧。
2. 候选边界由多种变化共同提出：谱变化、chroma/和弦变化、节奏活动变化、音色/嵌入变化。加上最短/最长片段约束，避免噪声导致切出大量极短段落。
3. 计算片段间相似度并形成 A/B/C 重复组。可使用节拍同步 chroma、MFCC/音色表示和节奏特征；对重复段落允许时间拉伸或轻微编曲差异。
4. 对比同一组的多次出现，判断段落内部是否有编曲加厚、旋律差异或尾部变化。副歌并不总是全曲最响，所以重复性和音乐内容应优先于响度阈值。
5. 如果暂时不接监督模型，只输出边界与 A/B/C 分组；不要为了满足字段格式而伪造 verse/chorus 标签。

### 阶段 D：可选的歌曲功能标签模型

可把现有规则与专门的音乐结构模型并行比较。All-In-One 是一个可评估的候选实现，公开说明支持 BPM、节拍、段落边界以及 intro/verse/chorus/bridge/outro 等功能标签，并能输出可视化/机器可读结果；其公开预训练模型基于 Harmonix Set 训练。它不是零成本依赖：项目说明列出 PyTorch、NATTEN 等安装要求，Windows 构建也需实际验证。先做独立适配器和小样本试验，不要直接把模型绑进核心提取流程。

模型输出处理建议：

- 保存原始预测分数，方便回溯；对外显示标签时再应用阈值和规则。
- 对模型没有覆盖的标签（例如模型不输出 pre-chorus）保留 unknown，不要从 verse/chorus 硬推。
- 统计不同语言、曲风、现场/录音室音源上的错误案例。训练数据与用户歌单不匹配时，模型结果可能偏差明显。
- 用户手工修正应可保存为人工真值，并用于后续本地评估；未明确授权前不要把用户音频上传到外部服务。

### 阶段 E：乐器、人声和和声层

第一版建议描述“变化证据”，暂不尝试数混音轨道：

- 能量/音色/打击活动随时间的变化可作为“编曲密度变化”代理，并清楚标为估计。
- 如需钢琴、吉他、弦乐、合成器、人声等命名标签，应接多标签音频分类器，并逐类输出置信度。
- 如需检测主唱、和声或合唱进入点，需要人声分离或人声活动模型，再比较人声 stem 的音高、声部数量代理和时间活动。
- HPSS 结果只叫 harmonic/percussive estimate；不得把它说成完成了人声/乐器分离。
- 评估混合声源中“乐器有几层”时，建议改成更可验证的描述，例如“低频层在 01:24 左右增强”“主唱后出现高音持续声部”；不要输出无法由模型核实的精确轨道数。

## 5. 推荐系统如何接入

推荐功能和分析展示共享底层特征，但应分开处理可信度：

1. 旧的能量阈值标签不要继续以高权重影响结构相似度。模型或新算法经过样本验证前，可暂时降低 `structure` 组权重，或只使用能量曲线相关性。
2. A/B/C 分组、段落边界和语义标签使用不同的相似度字段。比较歌曲结构时，可比较分段时长比例、重复组序列和动态轮廓，不应把“chorus”字符串序列当作唯一结构特征。
3. 新结构数据必须带 `analysis_version`。特征算法变化后，要能识别旧缓存并触发重算；数据库迁移需兼容老记录，避免一次更新使播放器读取失败。
4. 重新抽取特征是耗时工作，应支持后台/批量处理、进度、取消和失败重试；不要在播放器启动时同步扫描整库。
5. 推荐解释要引用真实依据，例如“能量轮廓相似”“重复段落比例接近”，而不是显示置信度不足的“副歌结构相同”。

## 6. 建议修改的文件边界

- `features/structure.py`：拆分全曲动态、边界检测、重复分组和标签推断；删除按索引交替标注类型的逻辑。
- `features/extract.py`：分别调度完整结构分析与可配置的局部推荐特征；记录分析窗口和版本。
- `features/harmony.py`：修正三和弦模板，并输出有意义的模板区分分数。
- `features/instruments.py`、`features/vocal.py`：明确代理量名称和置信度；新模型以可选适配器接入。
- `database/schema.py`、`database/repository.py`：新增或扩展结构 JSON/版本字段，提供旧库兼容和重算策略。
- `recommendation/space.py`、相关配置：避免低可信标签支配推荐；把动态相似和重复结构相似分开。
- `w-music` 的本地服务/界面：后续如要展示分析结果，再增加时间轴、可点击试听段落和人工修正入口。播放器不应自行复制 MIR 算法。

具体 schema 与 API 命名应先查项目当前版本，优先复用已有 `features_json` 或结构存储约定，不要重复新增等价字段。

## 7. 验收方式

准备 15–30 首用户熟悉的歌，覆盖：明显主副歌流行歌、动态平稳的民谣、摇滚/电子编曲、前奏较长、尾奏较长、桥段明显、重复副歌加厚、没有标准副歌的歌曲。每首至少人工标注主要边界、重复组、明确的主副歌/桥段（如无法确定则标 unknown），以及主观听到的动态事件。

验收分三层：

1. **边界**：候选段落起止是否靠近人工边界；统计边界容差内的 precision/recall 或 F1，并单独检查短段落。
2. **重复关系**：同一主题的副歌是否被分到同组；容易混淆的同和弦不同旋律段是否错误合并。
3. **动态描述**：build、peak、pull-back、release 的时间是否符合听感；检查被母带压缩、鼓声很强但情绪并未上升等反例。
4. **语义标签**：按标签统计混淆矩阵和 unknown 比例；“unknown”合理增加优于自信但错误的标签。
5. **推荐影响**：对照改造前后相似歌曲结果，确认新的结构特征提供可解释收益，而没有让其他相似度维度退化。
6. **性能与稳定性**：测量单曲和整库分析时间、内存占用、失败重试；验证旧数据库可打开且版本不匹配时能触发重算。

具体数值门槛应在第一轮人工标注后确定。不要先承诺未经数据验证的准确率。

## 8. 推荐实施顺序

1. 修复和弦模板错误；对结构标签降权/标记估计，避免继续放大错误结果。
2. 加入全曲低成本动态曲线，同时保留 45 秒特征窗口供现有推荐流程使用。
3. 加入可靠的边界和重复分组，先输出 A/B/C，不强求语义名称。
4. 用标注歌曲评估后，再试接 All-In-One 或其他功能标签模型；按需做 Windows 依赖、缓存和性能适配。
5. 最后评估乐器分类、人声和声分离与播放器时间轴 UI。

第一阶段的完成标准是：能用完整时间轴展示真实的强弱与编曲变化，能指出重复片段，并在证据不足时明确保留未知；它不要求第一版就准确识别所有歌的主歌、预副歌和桥段。

| 第 5 节：推荐侧降低低可信标签影响 | 已完成 | `space.py` 的 `structure` 相似度改三路混合（0.45 轮廓 / 0.30 重复组序列 / 0.25 时长占比），不比 label 字符串；权重仍 0.05 |
| 第 5 节：`analysis_version` 与旧库兼容 | 已完成 | `config.yaml: analysis.version` + `tracks.analysis_version`，增量扫描按版本判陈旧，端点返回 `stale` |
| 第 6 节：播放器时间轴 | 已完成 | w-music `Controls/StructureTimelineView` + `NowPlayingPage` 段落卡片；`GET /v1/analysis` |
| **第 7 节验收（15–30 首人工标注）** | **未做** | 需要用户本人标注；边界 F1、重复组混淆、事件符合听感、unknown 比例、推荐前后对照、性能稳定性六层里，目前只有自动化层面的证据 |

已知的诚实边界：本轮"分段是否合理"的判断建立在**合成 fixture**（可控的段落序列与响度包络）+ **真实曲库 19 首的分组分布**（ADR-25：阈值是在库层面按稳定度选出来的）+ 少量人工听过的曲目上，没有标注集，因此不给出准确率数字；边界 prominence、命名分位、事件幅度这些门槛仍是合成数据的量级初值，换真实曲库后应当用第 7 节的标注重新标定。分组这一项的真实音频证据只到"分布不再是退化的一整组"，**不等于每首都分对**。本机真实库（93 首）仍是改造前分析的，`analysis_version` 为 NULL —— 播放器会明说"旧版分析，没有全曲响度曲线"，重跑「分析曲库」后才有曲线。
